# FinSignal — 项目需求（工程视角整理）

> 本文档基于 `docs/requirements.md`（客户需求）整理而成，是工程团队对需求的拆解和落地方案，包含对开放问题的假设处理。客户需求本身以 `requirements.md` 为准，请勿在本文件中重复维护客户原始措辞。

## 这是什么任务

散户投资者被冗长的财务文档（10-K/10-Q 动辄几百页）压得喘不过气。市面上已有的 AI 工具能快速生成摘要，但都没有解决一个根本问题：用户分不清答案里哪句话是真的引用自原文、哪句话是模型编的。这不是"慢不慢"的问题，是"能不能信"的问题。

📌 **项目一句话描述：面向散户投资者的可验证引用式财报问答助手** —— 用户选定一只股票或上传财务文档，用自然语言提问，系统给出带逐句引用、带可信度评分的分析，并主动拦截或标记没有原文依据的结论。

## 核心功能（硬要求，每条都要做到）

| 要求 | 一句话 |
|---|---|
| 选股 / 上传文档 | 支持选 ticker，也支持上传 10-K、10-Q、8-K、财报电话会议纪要、新闻文档 |
| 长文档解析与检索 | 支持几百页量级文档的切分、索引、按需检索 |
| 自然语言问答 + 逐句引用 | 结论用大白话表达，但每条结论都能点回原文对应段落 |
| 逐条可信度评分 | 打分粒度是"每一句结论"，不是给整份报告打一个总分 |
| 编造内容检测与标记 | 主动识别、标出没有原文支撑的"幻觉"结论 |
| 自动化评测护栏 | 持续跑的评测集监控"无依据结论率"，超阈值就拦截或降级输出 |
| 引用溯源跳转 | 点一条结论能跳转到原文出处 |
| 报告导出 | 支持导出分析报告留存 |

## 生产质量要求

输入全部校验，不接受非法或缺失字段；一致性规则始终生效；出错时安全、清楚、可控，不裸抛异常；代码模块化、可维护；引用匹配和评分这类关键逻辑必须有自动化测试覆盖；评测护栏跟着每次模型/prompt 改动自动触发，不依赖人工手动跑；项目要能端到端开箱即用。

## 可信度处理规则

| 场景 | 处理方式 | 原因 |
|---|---|---|
| 结论有引用，且引用内容和原文对得上 | 正常展示，附可点击的原文链接 | 可验证，展示安全 |
| 结论没有原文支撑（无依据结论） | 标"未验证"警示，可信度分数下调，仍展示但需用户确认知晓 | 保持透明，风险不能被藏起来 |
| 结论明显与原文矛盾或过度推断 | 直接拦截，不展示，触发重新生成或人工复核 | 防止误导用户 |
| 同一用户对同一 ticker/文档重复提问 | 提示复用缓存结果或强制重新生成 | 省算力的同时保持内容新鲜 |
| 评测护栏检测到某批次无依据结论率超过阈值 | 该批次不上线，触发自动重试或人工复核 | 保护产品可信度底线 |

## 交付物与优先级

一份分析报告对应"一个用户问题 + 一个 ticker/文档"，必须包含：要点摘要、带引用的证据、逐条可信度分数、风险提示、未支持结论清单、免责声明。多市场覆盖和历史问答回看放二期，第一期集中打磨美股场景和评测闭环。

## 三个开放问题的假设处理方案（待客户/法务确认）

以下假设按市场通行做法给出，用于让项目先跑起来，正式立项前仍需与客户和法务确认。

### 关于监管合规

假设产品定位始终锁定在"信息整理与摘要展示"，不做个性化投资建议：所有输出只针对文档/ticker 本身做事实性分析和引用展示，不出现"建议买入/卖出/持有"这类操作性结论，也不把结论内容和用户的风险偏好字段做绑定生成（Risk Profile 字段可保留用于前端展示口径调整，但不用于改变分析结论本身）。全站保留显著免责声明。这只是工程假设，正式上线前必须请客户方的证券律师做合规意见确认。

### 关于标准答案集（Golden Test Set）的维护

假设由"分析师/内容团队 + 评测工程"共同拥有：分析师负责标注哪些结论算有依据、哪些算幻觉，工程负责把标注沉淀成自动化测试用例。更新机制是事件驱动而非固定周期：每次模型或 prompt 变更，全量跑一遍作为发布门槛；线上新出现的失败案例经人工复核后持续补充进集合；另设季度级别的系统性复审节奏。

### 关于无依据结论率阈值

假设分文档类型设定，而不是全局统一：结构化程度高的 10-K/10-Q 定得严一些（如 3%），语言更松散的新闻和电话会议纪要适当放宽（如 5–6%）。第一期数据量不够支撑精细分类型校准时，先用一个偏保守的统一阈值（4%）跑起来，积累线上数据后再拆分。
